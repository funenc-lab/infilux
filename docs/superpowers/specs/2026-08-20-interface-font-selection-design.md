# 界面字体方案选择设计

## 目标

修复“界面字体”设置中推荐字体方案的下拉选项与已选文本不一致的问题，并将字体配置收敛为受控的预设下拉选择。

## 范围与假设

- 范围仅限 Appearance Settings 的 Interface typography 区域。
- Terminal typography 不改动；它没有推荐字体方案下拉，且终端字体栈和 CJK 回退规则独立。
- 已持久化的 `fontFamily` 字符串保持兼容，不引入新的持久化字段或迁移；历史自定义值只读显示为自定义状态。
- 推荐方案继续按当前语言和平台生成；用户自定义的字体栈始终有效。

## 交互设计

仅保留“推荐字体方案”下拉：

- 下拉提供少量、受控且可解释的推荐方案，避免用户手写平台字体栈。
- 移除自定义字体栈输入框；新配置只能选择当前平台和语言推荐的字体方案。
- 当前字体栈匹配推荐方案时，触发器显示该方案的统一标签。
- 当前字体栈不匹配推荐方案时，触发器显示“Custom font stack”，并在下拉列表中以禁用项表达当前状态；选择任一推荐项后立即替换历史自定义值。
- 方案标签和触发器文本由同一个展示模型提供，避免在 JSX 中分别维护条件分支。

## 架构与扩展点

新增 settings 范围内的纯展示模型，负责：

1. 将推荐方案与当前字体栈解析为稳定的受控选择值。
2. 提供推荐方案、自定义方案的显示标签与可选状态。
3. 将持久化字体栈与 UI 选项解耦，保持 store 继续只拥有 `fontFamily`。

未来加入新的语言优先方案或平台方案时，只需扩展推荐方案生成器；展示模型会自动处理选中态和历史自定义值回退。

## 错误处理与验证

- 未识别的字体栈必须被解析为自定义状态，不得传入无对应项的 Select value。
- 不接受 `custom` 作为可写入字体栈的推荐方案，避免覆盖用户输入。
- 通过纯函数单元测试覆盖推荐匹配、自定义回退及展示标签的一致性。
- 通过现有 settings 类型检查和针对性 Vitest 运行验证。
